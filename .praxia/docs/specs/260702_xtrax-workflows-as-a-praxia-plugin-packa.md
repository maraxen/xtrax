# Brainstorm: xtrax workflows as a praxia plugin: packaging contract, rig-run dispatch, and drift gates

## Problem Frame
FIXED CONSTRAINTS (cannot change):
1. Plugins are not natively workflow-aware in praxia. xtrax mimics workflow-awareness via agent_assets/workflows/ template files + *_contract.yaml + [[plugin.workflows]] manifest entries. The packaging contract WORKS today; dispatch does NOT.
2. praxia owns all standard writes (plugin install/export write to ~/.praxia/). No forking praxia's asset pipeline — we consume it, we do not replace it.
3. Empirical facts we must design around, not wish away:
   - rig-run has a hardcoded nine-arm flow match (recon, reviewer, summarize, research, research_triangulate, procedural_recall, spec_draft_test, impl, recon_legacy); no generic/plugin entry; bail at rig_flow.rs:380-383. Plugin workflows resolve but cannot be dispatched.
   - strict-mode (ActionContract) tools are compiled Rust; plugin YAML cannot add tools.
   - an unregistered tool_profile silently yields an EMPTY registry (non-failing, tracing::warn only) — a toolless-strict-node hazard.
   - RigDispatchBackend is NO-CLAUDE (local backends only); port_validation is authored as a Claude PCW (7 role_step nodes, Claude roles, no action_mode). Dispatching it via rig-run would silently swap its execution substrate.
   - `praxia rig-run --flow recon` from xtrax cwd already failed template resolution (two root causes: workspace-ignoring registry dirs + a tier-2 dir missing all *_contract.yaml).
4. Any praxia-side change becomes a praxia-repo backlog item — a cross-repo dependency edge in the roadmap DAG. Deliverables MUST be partitioned explicitly xtrax-side vs praxia-side.

- How rig-run learns to dispatch a plugin flow (generic flow==template fallback vs a namespaced --flow xtrax:port_validation scheme).
- Where effectful/strict-mode tools come from (praxia-side generic sandboxed shell/bathos registry vs xtrax tools as a praxia crate feature vs routing all effectful actions through the bathos MCP). ## Pre-mortem Record
**User:** Six months out, definitive failure. The autopsy, top risks ranked:

PM-1 (highest — the beat's risk, realized): The phase-2 MCP-reachability probe was never run because phase-1 shipped and momentum died. The autoresearch loop was authored assuming bathos-MCP-in-Claude-PCW, but the loop got migrated to a NO-CLAUDE strict backend for cost, and every evaluate/commit node silently resolved to an EMPTY tool registry (G2). The loop ran for weeks producing fitness numbers with no execution-verified evaluator behind them — the exact MLR-Bench 80%-fabrication failure the whole design existed to prevent — and nobody noticed because the toolless-strict-node guard (O-2) was the deferred praxia edge that also never landed. Root cause: we let the two hard praxia edges (generic dispatch + toolless guard) drift apart; O-2 must ship WITH or BEFORE any strict-mode dispatch, not after.

PM-2: 14a flow==template fallback shipped, but the tool-less spec fallback it reuses turned out to strip context/tools that port_validation's PCW nodes actually needed, so plugin flows dispatched via rig-run behaved subtly differently from the same flow via dw emit → Claude. Two divergent execution paths for "the same" flow produced inconsistent verdicts; teams stopped trusting rig-run for plugin flows. Root cause: we never wrote a differential test asserting dw-emit-path and rig-run-path produce equivalent behavior for one shared flow.

PM-3: ORTHOGONAL-4's export-time SubFlow-ref rewriting was implemented as a naive string substitution and rewrote a substring that happened to match a child name inside an unrelated field (a prompt, a description), corrupting exported templates. The corruption was silent because the drift gate (D3) compared xtrax's authored source to the exported file and they matched — the rewrite was applied on BOTH sides. Root cause: the rewrite must be AST/field-scoped to SubFlow ref slots only, and D3 must compare the POST-rewrite expected export, computed independently, not just echo praxia's transform.

PM-4: 17c's opportunistic probe became a flaky-CI generator — the PyPI/git-tag probe fired in CI environments that DID have partial network, timed out intermittently, and flipped gates red on unrelated PRs. People added a blanket skip env-var, which then also suppressed the TTL loud-fail backstop, re-creating the exact silent-stale-gate defect (n9 OIDC) we set out to kill. Root cause: the probe and the TTL backstop shared one enable/disable switch; they must be independently controllable, and the probe must be strictly advisory (can only INVALIDATE, never satisfy, a gate).

PM-5: The first-consumer integration test (O-1) passed against a temp ~/.praxia but real installs hit a plugins.toml schema/version the test didn't fixture, and the drift-check's global-registry path (open Q3) turned out NOT to fire from xtrax cwd — so drift went undetected until an xtrax template edit shipped without re-export and a stale flow ran in production. Root cause: O-3's verification was treated as informational rather than as a gating precondition that flips D3 from recommended to mandatory.
