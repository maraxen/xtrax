# Brainstorm: Make the xtrax JAX library distribution-ready: pip-installable, PyPI-publishable, with CI, hosted docs, and high-quality README/API documentation.

## Problem Frame
FIXED constraints (cannot change):
- Python 3.13-only (requires-python>=3.13 is set; not relaxing to widen the matrix).
- Build backend stays hatchling, src-layout (already in place; not migrating to setuptools/flit/pdm).
- JAX-ecosystem conventions must be honored (typed, py.typed marker, autodoc-friendly, JAX-style API surface).
- Existing high-quality docstrings are the source of truth for API docs — autodoc must consume them, not duplicate them.
- Output-sink surface (io callbacks: BoundedCallbackHandler, async_indexed_stream re-exported from engine.io; checkpoint persistence via orbax) is IN SCOPE and must receive autodoc + README coverage.
- Real test coverage is 96.5% across 414 passing tests; the committed .coverage at 27.5% is stale and must be regenerated, not trusted.
- The version mismatch is a hard bug to resolve: pyproject says 0.2.0, __init__ says 0.1.0; single-sourcing must pick one truth.

NEGOTIABLE (open to divergence):
- Version single-sourcing mechanism (hatch-vcs from git tags vs __init__ read vs manual sync).
- License choice (MIT vs Apache-2.0).
- Docs tool (Sphinx vs MkDocs-material).
- Top-level re-export strategy (flat `from xtrax import Trainer, Engine` vs subpackage-explicit).
- CI shape (matrix breadth, coverage threshold value, PyPI Trusted Publishing OIDC vs token).
- How spec-implementation tasks get partitioned between a cursor-dispatch agent and a claude fixer.
- Whether main.py scaffolding is deleted or repurposed.

## Decision Log

JAX is never touched at build time, so the frame's 'eager JAX import at build' risk is overstated and idea 2 is build-safe. STEELMAN of runner-up idea 1 (hatch-vcs git tags): genuinely elegant single-truth (the tag), zero in-file drift, and pairs perfectly with OIDC tag-triggered publish — this is the strongest rival. It is REJECTED not because it is wrong but because (a) it adds a build-time plugin dependency and requires importlib.metadata.version() at runtime which raises PackageNotFoundError in editable/uninstalled dev trees (a real edge-case dev-UX paper-cut), and (b) it cannot itself RESOLVE the 0.1.0/0.2.0 mismatch — the first tag must still be chosen manually, so it does not reduce the load-bearing decision, only relocates it. edge-case lens: idea 2's one true failure mode is the regex moving/reformatting the __version__ line; mitigated by keeping __version__ as the literal FIRST executable line, above any re-export block. reversibility lens: idea 2 → idea 1 is a low-cost later migration (swap version source, add tag) once a green publish exists. Lowest-risk on the critical path.
- [MERGE] DIM1 VERSION companion: idea 23 (build-verification job) as REQUIRED safety net for idea 2: edge-case lens: idea 2's residual failure mode (regex reads a stale/zero/wrong version, or py.typed/data-file omitted from wheel) is SILENT at build time and only surfaces post-publish. idea 23 (build wheel → install into clean venv → `python -c "import xtrax; print(xtrax.__version__)"` + twine check) converts that silent failure into a CI gate.
