# Brainstorm: Generic fail-loud TOML-to-dataclass config primitive: extract the pattern from xtrax.cli.config's TrainConfig/load_config into a schema-agnostic, publicly reusable primitive for downstream consumers (e.g. plegadx's inference CLI) that need TOML-driven config loading without training-loop coupling

## Problem Frame
Fixed constraint: TrainConfig must not break (backward compat for existing `xtrax run`/`xtrax resume`/`xtrax sweep` consumers). Negotiable: where the generalized primitive lives (xtrax.cli.config vs a new module vs elsewhere). Additional requirement: this should be usable by more than just plegadx -- xtrax's other consumer surfaces too, not a one-off extraction for a single downstream package.

## Idea Pool
- [ai] FACTION A — Thin composable validators, no mega-function. Extract only the low-level primitives xtrax.cli.config's load_config already implicitly contains: (1) load_toml_document(path) -> dict (tomllib wrapper with consistent IOError/decode-error typing), (2) require_sections(raw, sections: list[str], error_cls: type[Exception]) -- presence check, (3) require_field(raw, name, predicate, error_cls) -- typed/validated field extraction (covers TrainConfig's custom `num_epochs must be positive int` and `seed must be int` checks, which are NOT bare type-hint checks). TrainConfig's load_config becomes a thin composition of these helpers; plegadx's InferConfig does its own composition with its own required sections/dataclass -- no shared dataclass-construction convention imposed. Strength: minimal surface, zero premature schema abstraction, doesn't force one "shape" of config validation on every domain. Weakness: doesn't collapse the "TOML -> validated dataclass" boilerplate as far as plegadx's own stated mirror-pattern implies they want -- downstream still hand-writes the dataclass construction call.
- [ai] FACTION B — Declarative schema-driven loader (single generic entry point). One function, e.g. load_toml_dataclass(path, dataclass_type, required_sections=..., schema_version=..., error_cls=ConfigError) -> T, that introspects the target dataclass's own type hints (dataclasses.fields / get_type_hints) to validate types and construct the instance in one call. TrainConfig's load_config collapses to a single call; plegadx's InferConfig does the same. Strength: maximal boilerplate collapse, matches plegadx's own stated "TOML -> validated dataclass, fail-loud ConfigError" intent almost verbatim -- the closest thing to "just reuse it." Weakness: real design risk -- TrainConfig's num_epochs/seed checks are custom predicates, not bare type-hint checks, so a pure type-hint-driven validator doesn't cover them without a per-field validator-injection mechanism (more API surface). Also the biggest exposure to the E2 pre-mortem's "seams rotted" failure mode: if the declarative schema doesn't actually fit InferConfig's real shape (e.g. optional sections, nested validation), plegadx ends up not using it after all and it's speculative surface that rots.
- [ai] FACTION C — Validator-composition toolkit (middle ground). Ship a small domain-agnostic module (location TBD -- see location fork) with: load_toml_document(path) -> dict (IO + parse, consistent error typing) and a tiny declarative validate_required(raw, spec: dict[str, FieldSpec]) where FieldSpec bundles a predicate + error message template, covering both simple presence checks and TrainConfig-style custom predicates (num_epochs positive, seed is int) via the same mechanism. Dataclass construction stays the caller's job (TrainConfig(**validated) is still hand-written) -- this stops short of Faction B's full auto-construction but goes further than Faction A's raw building blocks by unifying HOW a field gets validated (one FieldSpec vocabulary reused across every domain's config, rather than each domain hand-rolling its own require_field predicates). Strength: reusable validation vocabulary without committing to a single dataclass-construction convention that might not fit every future consumer. Weakness: introduces a new concept (FieldSpec) that has to earn its keep -- more design surface than Faction A, less payoff than Faction B.
- [user] Recorded three competing approaches (not evaluating yet):
- [user] FACTION A — thin composable validators (load_toml_document + require_sections + require_field), no shared dataclass-construction convention, each domain hand-composes.
- [user] FACTION B — one declarative load_toml_dataclass(path, dataclass_type, ...) entry point that auto-constructs the target dataclass from its own type hints.
- [user] FACTION C — middle ground: a shared FieldSpec-based validate_required() vocabulary (covering custom predicates like TrainConfig's num_epochs-positive check), but dataclass construction stays hand-written per domain.

## Decision Log
- [ACCEPT] Location: new top-level xtrax.config module (vs xtrax.cli.config or xtrax.io): xtrax.cli.config is disqualified because it doesn't fix plegadx's actual stated complaint (avoiding CLI-namespaced machinery). xtrax.io is disqualified as 'analogy not affinity' -- that namespace means array/sink I/O (zarr_integrity, callbacks), not config parsing. A new xtrax.config module is unambiguous and importable by any consumer without pulling in xtrax.cli. xtrax.cli.config's TrainConfig/load_config are refactored to import from xtrax.config, keeping them byte-compatible for xtrax run/resume/sweep.
- [ACCEPT] Land the extraction only in the same change that refactors TrainConfig.load_config onto it AND is consumed by a real downstream consumer: Directly mitigates pre-mortem scenarios 1 (fragmentation) and 3 (xtrax not eating its own dog food): a single canonical, actually-consumed refactor establishes the pattern before other consumers copy or diverge from it, rather than shipping an unproven paper contract nobody inside xtrax itself trusts.
- [ACCEPT] check_schema_version's mismatch semantics as an extensible structured result/exception hierarchy, not a fixed enum or flat boolean: Directly mitigates pre-mortem scenario 2: a real consumer needing a state the tri-state (missing/mismatched/newer-than-supported) doesn't cover (e.g. 'deprecated but still supported, warn') should be able to extend the taxonomy without a breaking signature change, rather than abandoning the primitive and writing their own version-check.

## Acceptance Criteria
**Given** the fixed constraint that `TrainConfig` must not break for existing `xtrax run`/`xtrax resume`/`xtrax sweep` consumers, the requirement that this serve >=3 real consumers (not just plegadx), and the winning design (Faction A: thin composable validators, plus `check_schema_version`), **when** implementing, **then**:

- **AC1 (missing schema_version).** Given a TOML document missing `schema_version`, when `check_schema_version(raw, current, error_cls)` is applied, then it raises `error_cls` naming the missing field — distinct from the mismatched/newer-than-supported cases (AC7).
- **AC2 (schema_version mismatch, extensible).** Given a TOML document whose `schema_version` does not match the caller's `current`, when `check_schema_version` is applied, then it raises an `error_cls`-rooted exception that distinguishes "older/mismatched" from "newer-than-supported" as part of an extensible hierarchy (AC7) — not a flat bool or single generic message.
- **AC3 (missing required section).** Given a TOML dict missing one or more required sections, when `require_sections(raw, sections, error_cls)` is applied, then it raises `error_cls` naming every missing section (not just the first).
- **AC4 (custom-predicate field validation).** Given a field value failing a caller-supplied predicate (e.g. `num_epochs <= 0`, `seed` not an int), when `require_field(raw, name, predicate, error_cls)` is applied, then it raises `error_cls` with a message naming the field and the offending value — `require_field`'s predicate parameter accepts an arbitrary `Callable[[Any], bool]`, not a fixed type-hint check (this is what disqualifies Faction B, per the Decision Log).
- **AC5 (TrainConfig refactor, byte-compatible).** Given `xtrax.cli.config.TrainConfig`/`load_config` refactored to compose `xtrax.config`'s primitives, when the full existing `tests/cli/test_config.py` suite (and any `tests/cli/` tests depending on `load_config`'s behavior) is run, then it passes unchanged — no observable behavior change for existing `run`/`resume`/`sweep` callers.
- **AC6 (domain-agnostic location, no CLI coupling).** Given `xtrax.config` is a new top-level module (per the Decision Log's location fork resolution), when a consumer imports `xtrax.config` directly, then no `xtrax.cli` or `tyro` machinery is imported as a side effect — verified by an isolation test mirroring `xtrax.cli`'s existing `assert "tyro" not in sys.modules` pattern (`tests/cli/test_entrypoint.py::TestImportIsolation`). `xtrax.config`'s primitives accept a caller-supplied `error_cls: type[Exception]` rather than hardcoding `xtrax.cli.errors.CLIError` (A2).
- **AC7 (extensible schema-version taxonomy).** Given `check_schema_version`'s missing/mismatched/newer-than-supported cases, when a future consumer needs an additional state (e.g. "deprecated but still supported, warn"), then the design accommodates it via a structured result object or exception-subclass hierarchy without a breaking signature change to `check_schema_version` itself — mitigates pre-mortem scenario 2.
- **AC8 (real-consumer adoption, not speculative).** Given the "land it with real consumers" decision, when this ships, then at least one real downstream consumer's adoption of `xtrax.config` (beyond xtrax's own internal `TrainConfig` refactor) is demonstrated before or alongside merge — mitigates pre-mortem scenarios 1 (fragmentation) and 3 (paper contract nobody trusts).
