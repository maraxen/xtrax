# Brainstorm: xtrax EDA visualization API design — dependency group, dashboard primitives, output formats (PNG/SVG/HTML), visualization library selection, transformation pipeline, metadata inclusion, and long-term integration hooks (tensorboard/wandb)

## Problem Frame
Fixed constraints: (1) xtrax core must stay free of viz dependencies — the eda group is strictly optional, (2) the stats.py layer must work with stdlib + numpy only (no pandas/matplotlib required), (3) output formats PNG, SVG, HTML are all required targets, (4) Python 3.10+ type signatures are required throughout, (5) the API must be testable without a display — headless rendering is mandatory. Negotiable: which viz library (seaborn vs plotly vs both), where transform_fn hooks land in the pipeline, whether metadata travels inline or as side-channel, the exact composition model for multi-panel dashboards, and the precise call-site shape of the public API.

## Idea Pool
- [user] PEGS map: Processes — stats extraction from BatchPlan, rendering to format, transform application, metadata embedding, dashboard composition, file/bytes output. Events — user calls plot fn, user saves output, CI pipeline captures artifact, notebook inline display. Goals — zero-boilerplate plan visualization, consistent cross-project artifacts, extensible to remote logging. States — raw BatchPlan, extracted stats dict (stdlib+numpy), optional DataFrame (if pandas present), Figure object (backend-agnostic), rendered bytes (PNG/SVG/HTML). Key assumptions to probe: (A) one viz backend is enough vs. two give better format coverage, (B) transform_fn is a pure function vs. a stateful pipeline, (C) metadata is always desired vs. opt-in, (D) dashboard is a fixed layout vs. user-composable.
- [ai] VIZ-LIB-A: Use seaborn-only as the viz backend. Seaborn wraps matplotlib and gives polished statistical plots (stripplots for strategy distribution, regplots for cardinality scatter) with a stable API. PNG/SVG output is native via matplotlib savefig. HTML output is produced by embedding the SVG into a minimal HTML template. Single dep chain: pandas + matplotlib + seaborn. Trade-off: no native interactivity, HTML is static SVG-in-HTML.
- [ai] VIZ-LIB-B: Use plotly-only as the viz backend. Plotly produces interactive HTML natively and can export PNG/SVG via kaleido (a subprocess-based renderer). Single dep chain: plotly + kaleido. Trade-off: kaleido is a heavy binary dependency that breaks in some headless CI environments (Docker without chromium). Static formats are second-class citizens.
- [ai] VIZ-LIB-C: Dual-backend design — seaborn for static (PNG/SVG), plotly for HTML. The public API detects which is available and routes accordingly, or the user sets XTRAX_EDA_BACKEND=seaborn|plotly. Both must be installed for full format coverage; either alone gives partial coverage with a graceful ImportError message. Trade-off: two dep chains, more surface to maintain, but best native quality for all three formats.
- [ai] VIZ-LIB-D: Use matplotlib-only (no seaborn). Matplotlib is sufficient for all required plot types (bar charts for strategy distribution, scatter for cardinality vs batch_size, histogram for bucket boundaries). Removes one dep (seaborn), keeps the same PNG/SVG capability, and avoids seaborn's opinionated theme defaults that may clash with user environments. HTML = SVG-in-template. Trade-off: more verbose plot code, less polished defaults.
- [ai] OUTPUT-API-A: Single render() function with fmt parameter. API: `render(plan: BatchPlan, fmt: Literal["png","svg","html"] = "png", path: PathLike | None = None) -> bytes | None`. Returns bytes when path is None (for notebook display or test assertion), writes to path otherwise. Clean single entry point, easy to mock in tests, extensible by adding fmt variants without new functions.
- [ai] OUTPUT-API-B: Separate format-specific functions. API: `to_png(plan, path=None) -> bytes`, `to_svg(plan, path=None) -> bytes`, `to_html(plan, path=None) -> str`. Explicit, discoverable via tab-completion, no fmt string to mistype. Trade-off: code duplication, harder to add new formats without multiplying functions, awkward for format-agnostic pipelines.
- [ai] OUTPUT-API-C: Figure abstraction class. API: `plan_figure = PlanFigure(plan)` then `plan_figure.save("out.png")`, `plan_figure.to_bytes("svg")`, `plan_figure.show()` (for notebooks). The Figure object holds the backend figure handle and exposes format-agnostic methods. Enables chaining: `PlanFigure(plan).with_transform(fn).save("out.html")`. Trade-off: stateful object, harder to reason about in functional pipelines, but cleanest for the tensorboard/wandb hook (log the Figure object).
- [ai] TRANSFORM-A: Pre-stats transform hook. The transform_fn operates on the raw BatchPlan before stats extraction: `render(plan, transform_fn=lambda p: filter_axes(p, strategy=Vmap))`. This lets users subset or modify the plan before any analysis. Trade-off: requires the user to know the BatchPlan API, less useful for post-extraction annotation.
- [ai] TRANSFORM-B: Post-stats transform hook. The transform_fn operates on the extracted stats dict: `render(plan, stats_transform=lambda s: {**s, "highlight": s["dedup_axes"]})`. Stats dict is stdlib+numpy, so the transform stays in the no-viz layer. Users can add derived metrics, filter axes, inject annotations. This is the most composable hook point because stats are the lingua franca between the two layers.
- [ai] TRANSFORM-C: Post-render figure transform. The transform_fn operates on the backend figure object (matplotlib Figure or plotly Figure): `render(plan, fig_transform=lambda fig: fig.update_layout(title="Run 42"))`. This enables user-side styling, annotation, and layout changes after xtrax has built the base figure. Trade-off: leaks the backend type into user code — the transform must know whether it gets a matplotlib or plotly figure, which breaks the abstraction requirement.
- [ai] METADATA-A: Inline metadata in HTML only. For HTML output, embed decision reasoning, strategy types, and memory estimates as data attributes on SVG elements or as a hidden JSON block in the page. PNG/SVG output is clean (no annotation). This is the simplest approach: metadata richness scales with format capability. For PNG/SVG users who want metadata, they must also export the stats dict separately.
- [ai] METADATA-B: Side-channel JSON sidecar. Every render call optionally writes a .json sidecar alongside the output file: `render(plan, path="plan.png", metadata=True)` → writes plan.png + plan.json. The JSON contains the full stats dict. This is format-agnostic and works for PNG/SVG/HTML equally. Downstream tools (CI, tensorboard plugins) can consume the sidecar independently of the visual artifact.
- [ai] DASHBOARD-A: Fixed-layout dashboard function. `plot_plan_dashboard(plan, path="dashboard.html")` always produces a 3-row layout: row 1 = strategy distribution bar chart, row 2 = cardinality vs batch_size scatter, row 3 = per-axis reasoning table. Fixed layout is predictable, testable, and requires no user composition knowledge. Named panels can be opt-in disabled via `panels={"strategy", "scatter"}`. This is the 80% case for xtrax users.
- [ai] DASHBOARD-B: User-composable panel registry. Users assemble dashboards from named panel primitives: `Dashboard([StrategyPanel(), CardinalityPanel(), BucketPanel(plan)])`. Each Panel is a callable that returns a figure or axes handle. Dashboard arranges them in a grid. Advanced users can write custom panels. Trade-off: more API surface, harder to test exhaustively, overkill for the initial use case.
- [ai] INTEGRATION-A: Logger protocol for tensorboard/wandb. Define a `PlanLogger` protocol (structural subtyping): `class PlanLogger(Protocol): def log_figure(self, tag: str, figure: bytes, fmt: str, step: int) -> None: ...`. The render API accepts an optional logger: `render(plan, logger=wandb_logger, step=epoch)`. Users wrap their wandb/tensorboard writer in a thin adapter. xtrax never imports wandb or tb — the dependency stays outside. This is the minimum surface needed for remote logging.
- [ai] STATS-LAYER: Pure stats/viz separation contract. stats.py exports: `extract_plan_stats(plan: BatchPlan) -> dict[str, Any]` (stdlib+numpy only, importable from core without eda extras), `analyze_dedup(decision: AxisDecision) -> DedupStats`, `analyze_bucket(decision: AxisDecision) -> BucketStats`. viz.py imports stats.py but stats.py never imports viz.py. The eda extras guard lives in viz.py's module-level import block with a clear ImportError message pointing to `pip install xtrax[eda]`.
- [ai] ASSUMPTION-REVERSAL: What if the stats dict is the primary output, not the figure? Invert the design — `explain_plan(plan)` returns a rich PlanStats dataclass that can be serialized to JSON, rendered to any format, or logged directly. The viz functions become thin formatters over PlanStats rather than top-level entry points. This matches how tools like wandb actually ingest data (as structured metrics, not images), and makes the stats layer the stable public API while viz is a convenience layer.

## Decision Log
- [REJECT] VIZ-LIB-C: Dual-backend seaborn + plotly: 2x maintenance cost for a small library; reversibility analysis shows seaborn-only can add plotly later without API breakage, but dual-backend cannot be simplified without breaking users. Dep chain complexity not justified at v0.1 of eda layer.
- [REJECT] VIZ-LIB-B: plotly-only backend: kaleido is a subprocess-based binary renderer that breaks in headless Docker CI without chromium. Static formats are second-class. Headless rendering is a fixed constraint — plotly fails it without extra system deps.
- [REJECT] OUTPUT-API-B: Separate format-specific functions (to_png, to_svg, to_html): Code duplication multiplies maintenance burden when adding new formats; awkward for format-agnostic CI pipelines that take fmt as a parameter. Single render() with fmt Literal is strictly better.
- [REJECT] OUTPUT-API-C: PlanFigure abstraction class with .show(): .show() requires environment detection (Jupyter vs terminal) which adds IPython dependency or runtime sniffing. Without .show() the class provides minimal value over a render() function. The abstraction leaks when users need backend-specific styling. Defer to a future version if the need arises.
- [REJECT] TRANSFORM-C: Post-render figure transform (operates on matplotlib/plotly Figure object): Leaks backend type into user code. User's transform_fn must know whether it receives a matplotlib or plotly Figure, breaking the abstraction requirement established in Phase 1. Post-stats transform (TRANSFORM-B) achieves the same flexibility without the leak.
- [DEFER] DASHBOARD-B: User-composable panel registry with Panel classes: Valid design for advanced users but overkill for v0.1. Defer to v0.2 once fixed-layout dashboard proves adoption. The fixed-layout dashboard (DASHBOARD-A) with panel filter set covers the 80% case and is far easier to test.
- [ACCEPT] VIZ-LIB-A: seaborn-only backend for PNG/SVG/HTML: Provides polished statistical plots native to the domain (stripplots, regplots, barplots). PNG/SVG via matplotlib Agg backend (headless). HTML via SVG-in-template (no kaleido, no subprocess). Single dep chain: pandas + matplotlib + seaborn. Reversible: plotly can be added as optional second backend later without breaking the render() API.
- [ACCEPT] OUTPUT-API-A: Single render() function with fmt Literal parameter: Clean single entry point. Returns bytes (PNG/SVG) or str (HTML) when path is None, writes to path otherwise. Extensible by adding fmt variants. Easy to mock and assert in tests. Signature: render(plan, view="dashboard", fmt="png", path=None, stats_transform=None, metadata=False, logger=None, step=None).
- [ACCEPT] TRANSFORM-B: Post-stats transform hook on stats dict: Stats dict is stdlib+numpy — the transform stays in the no-viz layer, is pure, and is composable. Users can filter axes, add derived metrics, inject annotations. This is the correct hook point because stats are the lingua franca between the two layers.
- [ACCEPT] METADATA-B: Side-channel JSON sidecar: Format-agnostic metadata delivery. Works for PNG/SVG/HTML equally. Downstream CI tools and tensorboard plugins consume sidecar independently of visual artifact. Opt-in via metadata=True parameter. Sidecar is named {stem}.json alongside the output file.
- [ACCEPT] DASHBOARD-A: Fixed-layout dashboard with panel filter: Predictable 3-row layout covers the 80% case. panels= set parameter allows opt-out of specific panels without requiring user composition knowledge. Testable: every panel has a known position and content. Extensible by adding new panel names to the registry without breaking existing callers.
- [ACCEPT] INTEGRATION-A: PlanLogger structural protocol: Defines log_figure(tag, figure, fmt, step) as a structural Protocol. xtrax never imports wandb or tensorboard. Users provide a thin adapter. This is the minimum surface for remote logging and does not require any new dependencies in xtrax itself.
- [ACCEPT] STATS-LAYER: Pure stats/viz separation — stats.py uses only stdlib+numpy: stats.py importable from xtrax core without eda extras. explain_plan() and extract_plan_stats() are the primary public API. viz.py is a convenience layer on top. ImportError for viz functions points to pip install xtrax[eda].
- [ACCEPT] ASSUMPTION-REVERSAL: explain_plan() / PlanStats as primary API, viz as convenience: Matches how wandb/tensorboard actually ingest data (structured metrics, not images). PlanStats dataclass is JSON-serializable and stable. Viz functions are formatters over PlanStats. This makes the stable public surface the stats layer, not the rendering layer, which is correct for a long-term API.
- [REJECT] CRITIQUE-VIZ-LIB: "plotly addable later without API breakage": [CRITIC] idea=VIZ-LIB-A lens=api_design finding=The claim "no API breakage" conflates function signature stability with output semantics — render(fmt="html") today returns static SVG-in-HTML bytes; adding plotly later changes the same call to return interactive plotly HTML, which is a silent semantic breaking change for any downstream tool that parses or embeds the HTML output. severity=MAJOR
- [REJECT] CRITIQUE-TRANSFORM: stats dict has no schema contract: [CRITIC] idea=TRANSFORM-B lens=api_design finding=stats_transform: Callable[[dict], dict] has no documented key schema — a user writing a transform function is programming against an unversioned interface; if extract_plan_stats() renames a key in a patch release, transform functions silently receive a different dict and either KeyError at runtime or silently no-op the intended mutation with no diagnostic. severity=MAJOR
- [REJECT] CRITIQUE-SIDECAR: metadata=True with path=None is unspecified: [CRITIC] idea=METADATA-B lens=edge_cases finding=The sidecar contract says "written alongside the output file" but all 8 acceptance criteria supply a path — render(plan, metadata=True) with no path has unspecified behavior: silently ignore, raise ValueError, or write to a temp path; none is specified, making the API's in-memory + metadata combination a silent no-op or runtime error depending on implementation choice. severity=MAJOR
- [REJECT] CRITIQUE-SIDECAR-CONCURRENCY: sidecar write is not atomic: [CRITIC] idea=METADATA-B lens=second_order_effects finding=Two concurrent render() calls targeting the same path write the image then the sidecar as separate non-atomic operations — a reader arriving between the two writes sees a fresh image paired with a stale or absent sidecar, which is a data-consistency hazard for CI pipelines that consume both artifacts. severity=MINOR
- [REJECT] CRITIQUE-LOGGER: log_figure(figure: bytes) breaks on HTML format: [CRITIC] idea=INTEGRATION-A lens=api_design finding=PlanLogger.log_figure is typed as figure: bytes but render(fmt="html") returns str — any adapter that implements the protocol as written will receive a str when logging HTML output and must handle bytes | str; the protocol type is internally inconsistent with the accepted render() return type, meaning no fully correct adapter can be written without casting or re-encoding. severity=FATAL
- [REJECT] CRITIQUE-STATS-LAYER: return type of extract_plan_stats() is unspecified: [CRITIC] idea=STATS-LAYER lens=feasibility finding=The decision says stats.py is "stdlib+numpy only, importable from core without eda extras" but does not specify the return type of extract_plan_stats() — if it returns a pandas DataFrame (natural for plan data), the constraint is violated; if it returns dict[str, Any] with numpy arrays the constraint holds but the TRANSFORM-B dict schema gap applies; the underspecification leaves the constraint un-verifiable at design time. severity=MAJOR
- [REJECT] CRITIQUE-DASHBOARD: panels= is an unvalidated free-form string set: [CRITIC] idea=DASHBOARD-A lens=edge_cases finding=The panels= parameter is specified as a set of string names with no enumeration of valid values and no defined behavior for unknown names — a typo like panels={"strategyyy"} has unspecified behavior (silent all-panels, silent empty, or ValueError), making the parameter a silent misconfiguration trap; the acceptance criterion only tests the happy path. severity=MAJOR
- [REJECT] CRITIQUE-ACCEPTANCE: empty BatchPlan not covered by any acceptance criterion: [CRITIC] idea=OUTPUT-API-A lens=edge_cases finding=None of the 8 acceptance criteria cover render(BatchPlan()) with zero axes — an empty plan produces empty stats, which causes seaborn to error on empty DataFrames (stripplot with no data raises ValueError) or produces division-by-zero in cardinality scatter normalization; this is a first-contact edge case likely hit during development setup, not production. severity=MAJOR
- [REJECT] CRITIQUE-RETURN-TYPE: render() return type is bytes | str | None but typed as bytes | None: [CRITIC] idea=OUTPUT-API-A lens=api_design finding=Acceptance criterion 2 requires render(fmt="html") to return a str containing "<svg>" but the decided signature is render(...) -> bytes | None — callers doing result.decode("utf-8") on HTML output will succeed only if str is silently encoded to bytes first, which is ambiguous; the return type must be bytes | str | None and the type dispatch must be explicit or HTML must always return bytes; the inconsistency will surface as a mypy error or runtime AttributeError. severity=FATAL

## Pre-mortem Record
**User:** Pre-mortem: The design failed because seaborn's HTML output (SVG-in-template) was not interactive, and users who expected clickable tooltips on the strategy scatter plot were disappointed and wrote their own plotly wrappers instead. Over 6 months, three different projects each independently wrote a plotly adapter for the stats dict, and none of them used the render() function. The stable part — explain_plan() and PlanStats — was used everywhere. The viz layer was effectively abandoned. What this tells us: the render() API should not be the long-term stability anchor; PlanStats is. The fix is already in the winner: PlanStats-first design ensures the stable API surface is correct. For the render() layer, the mitigation is to document clearly that it is a convenience function with no interactivity guarantee, and to make it easy to pass PlanStats directly to plotly for users who want HTML interactivity. No API change needed — the failure mode is a documentation and expectation gap, not a design flaw.
