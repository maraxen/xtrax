# Brainstorm: HMW design the xtrax run verb: drive a training run from a config file, reusing the engine/training/data runtime, without reimplementing what equinox/optax/the existing Engine already do

## Problem Frame
FIXED constraints (cannot change): (1) Delegation-not-reimplementation — run must reuse the existing Engine.fit_sync, Trainer, DataModule, optim helpers, and equinox/optax/orbax; it is glue, never a new training loop. (2) Must reuse the E2 cli/loader.py load_fn('pkg:sym') for every string→object resolution. (3) import xtrax and import xtrax.cli stay tyro-free (tyro inside main only); new deps land in the cli extra. (4) DataModule's signature is DataModule(dataset:Any, batch_size) — a config file cannot pass a live Python object, so SOME resolution seam is unavoidable. (5) ResumableState is assembled by hand today; some init path is needed.

NEGOTIABLE: config schema shape (flat vs nested, typed RunSpec vs raw TOML); WHERE the data-resolution and state-init glue lives (cli layer vs promoted into training/engine public API); whether run-MVP emits a manifest now or defers it; whether the E1 axis-RunSpec concept connects to the train-config or is fully orthogonal; run-id scheme and location.

Frame is locked — proceed to diverge.

## Idea Pool
- [ai] [FORK 2 — DataModule resolution] Option A: "Loader-resolved dataset object." Config carries `[data]` with `factory="my_pkg:load_train"` plus kwargs. `run` resolves the symbol via the existing cli/loader load_fn, CALLS it to get a live dataset object, then constructs `DataModule(dataset, batch_size)` itself. Zero new runtime API surface — DataModule is untouched, the loader does all string→object work. The config points at a callable that returns the raw dataset (grain/array/whatever DataModule already accepts), batch_size stays a top-level/[data] scalar that run passes in. Maximally aligned with delegation: run is pure cli-layer glue.
- [ai] [FORK 2 — DataModule resolution] Option B: "Factory-returns-DataModule." Config `[data]` carries `factory="my_pkg:make_datamodule"` and run resolves+calls it, expecting the user's callable to return a fully-built DataModule (not a raw dataset). run never touches batch_size or DataModule construction. Pushes ALL data-assembly responsibility to user code; run only type-checks the return is a DataModule. Thinnest possible run-side glue, but leaks the batch_size/tiling knobs out of the config into user code — weakest config-as-source-of-truth.
- [ai] [FORK 2 — DataModule resolution] Option C: "DataModule.from_config / from_path classmethod." Add a new public runtime constructor on DataModule that accepts an import-path string + kwargs + batch_size and does the load_fn resolution internally. run just passes the [data] table through. Cleanest config→DataModule mapping and makes the runtime usable from non-CLI callers, BUT adds permanent public runtime API surface AND couples the data layer to the cli loader (or duplicates load_fn into data/), violating the "loader lives in cli" boundary unless load_fn is promoted to a shared util first.
- [ai] [FORK 2 — DataModule resolution] Option D: "Registered dataset-factory protocol." Define a DatasetFactory Protocol/entry-point registry; config names a registered key (`data="mnist"`) rather than an import path, run looks it up in a registry dict. Most ergonomic for end-users and gives named, discoverable datasets, BUT introduces a whole registration mechanism + global registry state, duplicates what the import-path loader already does, and is the heaviest new surface — least aligned with delegation/MVP.

Gives users both ergonomics with a single config surface and zero new runtime API — the only cost is a runtime isinstance branch in cli glue and a slightly less-strict contract. Likely the most live option: strictly dominates A and B on flexibility at near-zero added surface.
- [ai] [FORK 5 — scope boundary] Option F: "Thinnest run-MVP, manifest fully deferred." run = {resolve model/optimizer/data from config → init_state → fit_sync to completion → exit}. No manifest, no run-id, no checkpoint-index written by run beyond whatever orbax already drops in checkpoint_dir. Smallest coherent unit; mirrors how E2-MVP deferred lifecycle verbs. Risk: resume later has NO contract to build against and may force a breaking change to run's output.
- [ai] [FORK 5 — scope boundary] Option G: "run-MVP WITH a minimal manifest seam." run does everything in F PLUS writes a tiny JSON manifest to .xtrax/runs/<id>/manifest.json capturing {run_id, model import-path + kwargs (so resume can rebuild state_template), optimizer path, checkpoint_dir, config-hash, schema_version}. run-id = config-hash (deterministic, dedups identical runs) with a uuid fallback for collisions. Manifest is WRITE-ONLY in MVP (resume not implemented), but it locks the contract resume will read. Costs ~one emit module reusing cli/emit.py's {_meta:{schema_version}} machine-contract. Bias-toward-this per the "design-for the seam even if minimally implemented" directive.

Keep it tyro-FREE by hydrating from the dict manually (tyro stays for argv only) so import xtrax.cli stays tyro-free. Costs a schema module but gives resume/sweep a typed object to share. The fix the spec must mandate now: assert each invariant at the write/construction site with a test, and stamp schema_version so a versioned migration is possible rather than a silent break.
