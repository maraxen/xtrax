# Brainstorm: Entry-points-based xtrax CLI verb registration: should xtrax.cli.registry.REGISTRY gain a plugin hook (e.g. importlib.metadata.entry_points) so downstream packages can register their own tyro-dispatched verbs into the xtrax CLI, and if so, what should that hook look like

## Problem Frame
Fixed constraints: (1) Cannot reintroduce a custom register_verb() API -- the E2 auto-CLI brainstorm already rejected that on rot-surface grounds. (2) Cannot change REGISTRY/entrypoint.py's existing behavior for xtrax's own built-in verbs. (3) Must honor the same demand-gating discipline idea-004's own idea log and the E2 pre-mortem already established -- don't ship speculative extensibility ahead of real, demonstrated demand.

Negotiable: whether to build this now, defer it, or document it as a recipe instead of code; if built, the entry-points group name, verb-name-collision precedence rules (built-in vs plugin), the failure-mode contract for a malformed/broken plugin entry point, and whether it's opt-in or always-on.

## Idea Pool
- [ai] FACTION A — Build now: entry_points hook, as idea-004 originally proposed. importlib.metadata.entry_points(group="xtrax.cli.verbs") scanned in registry.py, merged with the built-in dict at CLI startup. Downstream packages declare verbs via their own pyproject.toml [project.entry-points."xtrax.cli.verbs"] section, so their verb gets dispatched as `xtrax <their-verb>` through xtrax's own binary. Needs resolving: collision precedence (built-in vs plugin verb name clash), and where/when a broken plugin entry point fails (CLI startup vs lazy at dispatch).
- [ai] FACTION B — Defer entirely; keep as a documented-but-unbuilt upstream ask. Matches idea-004's own stated framing verbatim: "optional/upstream ask... demand-gated on >=2 real consumers wanting to extend the xtrax CLI itself; plegadx's audit is currently the only demand signal." No code, no implementation-ready spec -- just a short decision record explaining what would trigger revisiting it. Directly extends the idea-003 runner-up logic (both independent advisors in that session flagged "don't build shared/extension machinery for one consumer" as correct) -- and idea-004's demand signal is weaker than idea-003's ever was.
- [ai] CRITICAL FINDING (re-reading idea-004's own source text, and this whole conversation's history with plegadx): plegadx is building ITS OWN separate CLI binary ("mirroring xtrax's dispatch pattern... for their own FU-5 CLI"), not asking for their verb to run as `xtrax <plegadx-verb>` through xtrax's own binary. idea-004's entry_points proposal (Faction A) would make a plugin verb dispatch through XTRAX's binary -- a capability nobody, including plegadx, has actually asked to consume. Even plegadx's own audit only "flagged this as optional," they never requested it as something they'd use. This means the real demand signal for Faction A specifically (verb dispatch THROUGH xtrax's own CLI) is not just "one consumer" -- it may be ZERO consumers with an actual concrete need, as distinct from idea-003 where plegadx has a real InferConfig shape in hand today.
- [ai] FACTION C — Document a different, already-possible pattern instead: xtrax.cli.registry.REGISTRY is already a plain importable module attribute (`from xtrax.cli.registry import REGISTRY`) even though it's not in xtrax.cli.__all__. A downstream package building its OWN separate tyro-dispatched CLI (which is what plegadx is actually doing) can already compose `{**REGISTRY, **their_own_verbs}` into their own subcommand_cli_from_dict call today, with zero xtrax changes -- reusing xtrax's own verbs (plan/explain/export/etc.) inside a plegadx-branded CLI if they ever want that, without needing xtrax's binary to host plugin verbs at all. This solves a DIFFERENT (narrower, already-real) need than Faction A's entry_points hook, and requires only a documentation change (using-xtrax skill note), not new code -- same zero-design-risk shape as the load_fn formalization already shipped this session.
- [user] Most drawn to: Faction C (document REGISTRY-composition as a sanctioned pattern for a downstream package building its own separate CLI, plus fix the export gap -- add REGISTRY to xtrax.cli.__all__, not just xtrax.cli.registry.__all__) combined with Faction B (explicit defer decision record for Faction A's entry_points hook).
- [user] Risk/false assumption to name: both independent advisors flagged that Faction C, if shipped as pure documentation without the __all__ fix, would make "already possible" false for the actually-recommended import path -- a later consumer could copy the deep-module-import as if sanctioned, when it isn't declared stable. That's the assumption that could break this: "REGISTRY is already public enough to document" is false today; it needs the one-line __init__.py export fix to become true.

## Decision Log
- [ACCEPT] Document REGISTRY's keys/dict-shape as stable, but mark the (ArgsClass, run_fn) tuple's internal typing as provisional: Mitigates pre-mortem scenario 1 (silent contract drift): a downstream composer relies on the dict shape (verb name -> callable pair), not necessarily every internal typing detail of ArgsClass/run_fn, so documenting the narrower real contract avoids over-promising stability xtrax isn't ready to test-gate yet.
- [ACCEPT] Add an integration test in xtrax's own suite exercising {**REGISTRY, **fake_downstream_verbs} through tyro.extras.subcommand_cli_from_dict: Mitigates pre-mortem scenario 3: catches a real verb-name or ArgsClass field-name collision under tyro's dispatch/help-text generation before a real downstream consumer hits it as an emergency bug report.
- [ACCEPT] Update praxia idea-004 itself (rather than a separate static prose decision record) to carry the defer decision and its explicit revisit trigger: Mitigates pre-mortem scenario 2 (trigger never gets checked): idea-004 already exists as a tracked, re-visitable praxia artifact -- updating its status/body to state the precise trigger (a second real downstream package independently requesting dispatch-through-xtrax's-own-binary) gives the trigger an actual owned home instead of a static markdown file nobody re-reads.
- [ACCEPT] Bind any future Faction A implementation to entrypoint.py's existing AC2 lazy-import discipline: an entry_points scan must happen inside main(), not at registry.py's module top level: The code-architecture-advisor found that entrypoint.py imports REGISTRY (and thus all 9 built-in verb modules) eagerly at module top level, while keeping tyro itself strictly lazy (AC2). An entry_points scan for downstream ArgsClass/run_fn pairs would need its own lazy-loading tier plus per-entry-point exception isolation to avoid violating that same discipline -- recording this now as a binding constraint prevents the cost from being rediscovered from scratch if Faction A is ever revisited.

## Acceptance Criteria
**Given** the fixed constraints (no custom `register_verb()` API; no change to `REGISTRY`/`entrypoint.py`'s existing built-in-verb behavior; honor the same demand-gating discipline as the E2 pre-mortem) and the winning design (Faction C + B: document the composition pattern, defer the entry_points hook), **when** implementing, **then**:

- **AC1 (export gap fixed).** Given `REGISTRY` is today only importable via `from xtrax.cli.registry import REGISTRY` (not from `xtrax.cli` directly), when the export gap is fixed, then `from xtrax.cli import REGISTRY` resolves to the same dict object and `"REGISTRY"` appears in `xtrax.cli.__all__`.
- **AC2 (documented, bounded stability contract).** Given a downstream package wants to compose `{**REGISTRY, **their_own_verbs}` into their own `tyro.extras.subcommand_cli_from_dict` call, when this pattern is documented (using-xtrax skill's CLI Layer section), then the documentation explicitly declares `REGISTRY`'s keys and dict shape (`verb_name -> (ArgsClass, run_fn)`) stable, while marking the `ArgsClass`/`run_fn` internal typing as provisional (not a versioned public contract) — mitigates pre-mortem scenario 1.
- **AC3 (composition pattern tested).** Given the composition pattern, when a new integration test is added to xtrax's own suite exercising `{**REGISTRY, **fake_downstream_verbs}` through `tyro.extras.subcommand_cli_from_dict` (a merged dict from two sources, per assumption A2 — not `REGISTRY` alone), then it passes, and would fail loudly on a verb-name or `ArgsClass` field-name collision — mitigates pre-mortem scenario 3.
- **AC4 (Faction A explicitly deferred with a precise trigger).** Given Faction A (the `entry_points` hook) is deferred, when the decision is recorded, then it states the exact revisit trigger: a second real downstream package independently requesting dispatch-through-xtrax's-own-binary specifically (not "extending the CLI" in the abstract, and not satisfied by a package merely wanting the composition pattern from AC2/AC3).
- **AC5 (trigger has a tracked, owned home).** Given praxia `idea-004` already exists as the tracking anchor for this capability, when this spec finalizes, then `idea-004`'s status/body is updated to reflect the defer decision and AC4's exact trigger text, rather than being left as an unresolved "optional ask" — mitigates pre-mortem scenario 2 (trigger never gets checked).
- **AC6 (AC2 lazy-import constraint bound for any future revisit).** Given `entrypoint.py`'s existing lazy-`tyro`-import discipline (its own AC2), when Faction A is ever revisited, then any `entry_points` scan must happen inside `main()` (or an equivalently lazy point), never at `registry.py`'s module top level — recorded now as a binding constraint so this cost isn't rediscovered from scratch later.
- **AC7 (zero behavior change today).** Given this spec ships only documentation, one `__init__.py` export line, one new test, and a praxia `idea-004` status update, when it lands, then `registry.py`'s existing 9-verb `REGISTRY` dict and `entrypoint.py`'s dispatch logic are unchanged — no behavior difference for xtrax's own CLI.
