## Problem Frame
FIXED constraints (cannot change):
- The three gate functions themselves (`compute_ratchet_decision`, `create_pending_commit`/`advance_best_so_far`, `measure_two_phase_timing`/`assert_no_compile_time_regression`) are already implemented, tested, and proven composable in scripts/smoke_2181_walking_skeleton.py -- this brainstorm does not redesign them.
- `run_one_candidate_pass` (controller/main_loop.py) is the real per-candidate call site; it currently dispatches via `record_candidate_run` -> `BathosCampaignAdapter.run` (controller/lineage_interim.py), returning a `CandidateRunResult(script_path, exit_code, success)` -- no fitness dict, no output artifacts on the result itself (though `output_paths` is a parameter the caller already supplies).
- A candidate must be bathos-dispatched (run as an out-of-process script via bathos) exactly ONCE per pass -- backlog #4137 exists specifically to prevent a second, redundant dispatch of the same candidate.
- `BathosSplitComputeEvaluator` (controller/evaluate_adapter.py, #4133/PR #86) already exists and implements SPLIT_COMPUTE (dispatch via campaign_adapter.run -> score in-process against a locked `ClosureManifest.split_paths`) for a different call site -- we are not redesigning it, only deciding whether/how `run_one_candidate_pass` reuses it.
- `multi_metric_ratchet.compute_ratchet_decision` requires two same-keyed fitness dicts (candidate + current-best) plus a `higher_is_better` map -- it never fetches its own inputs.
- Nothing may fabricate or trust a subprocess-self-reported fitness number (the whole reason SPLIT_COMPUTE exists).

NEGOTIABLE:
- Whether `run_one_candidate_pass` keeps its own `record_candidate_run` dispatch call or is refactored to call `BathosSplitComputeEvaluator` as its sole dispatch+score path.
- Whether "dispatch" and "score" get split into two independently-callable functions/methods (possibly requiring a small refactor inside `BathosSplitComputeEvaluator` or a sibling module) versus one of them being reused wholesale.
- Where "current best" fitness/state is read from (a persisted ref, an in-memory campaign-loop variable, etc.) -- not fixed by any code I've read yet.
- Exactly where the ratchet-crash-atomicity commit/reset and compile-time-clock measurement attach in the post-decision control flow.
- Whether the winning design changes `OneCandidatePassResult`'s shape (e.g. adding a `ratchet_decision` field) or composes ratcheting as a second function layered on top.

## Idea Pool
- [user] Five candidate architectures for how run_one_candidate_pass obtains its fitness dict without double-dispatching bathos:
- [user] A. REPLACE dispatch call site: refactor run_one_candidate_pass to drop record_candidate_run/adapter.run entirely and call BathosSplitComputeEvaluator's existing evaluate()-style method as its sole dispatch+score path. One dispatch call site, period -- lineage_interim.py's record_candidate_run becomes dead code for this path (may still serve #4133's original call site if that one still needs it, or may itself need updating to also flow through the evaluator).
- [user] B. SPLIT dispatch/score into two callables: refactor BathosSplitComputeEvaluator (or add a sibling) so "dispatch and get raw artifacts" and "score already-obtained artifacts against ClosureManifest" are two independently-callable pieces. run_one_candidate_pass keeps its existing record_candidate_run dispatch call unchanged, then calls the new score-only piece directly with the output_paths it already has as its own parameter (CandidateRunResult doesn't need to carry them back). Two call sites, but only one of them (dispatch) ever touches bathos.
- [user] C. MERGE the lineage and evaluation call paths: go further than A -- fold lineage_interim's derived_from-resolution responsibility directly into whatever wraps BathosSplitComputeEvaluator's dispatch step, so there is exactly one dispatch+lineage+score call in the whole codebase, and lineage_interim.py's record_candidate_run is retired outright rather than left as an unused parallel path for some other caller.
- [user] D. PROTOCOL-LEVEL decoupling: define a CandidateDispatcher/CandidateEvaluator protocol that run_one_candidate_pass depends on abstractly; BathosSplitComputeEvaluator becomes the sole production implementation registered against it. Same end-state as A but framed to decouple the caller from the concrete evaluator class, so a future different split-compute strategy doesn't require touching main_loop.py again.
- [user] E. RELOCATE the ratchet concern to the loop level: leave run_one_candidate_pass's dispatch and OneCandidatePassResult contract completely unchanged (still record_candidate_run, still no fitness dict on the result). Add a NEW, separate function called by the multi-iteration driver (not by run_one_candidate_pass itself) that takes the pass result's output_paths, calls BathosSplitComputeEvaluator's scoring-only piece (no dispatch), gets the fitness dict, and only THEN runs compute_ratchet_decision + the crash-atomicity commit/reset + compile-time-clock check. This keeps run_one_candidate_pass's scope stable and puts the whole ratchet pipeline one layer up.
- [user] One more, genuinely orthogonal to A-E: F. DUAL-PATH self-check instead of single-path replacement -- keep BOTH record_candidate_run's dispatch (unchanged) and add a lightweight assertion that BathosSplitComputeEvaluator is never separately invoked for the same candidate within the same pass (e.g. a shared campaign-scoped dispatch-ledger keyed by content_sha256 that both code paths must consult before calling adapter.run, raising loud on a second attempt for the same hash). This treats "no double dispatch" as an enforced invariant/guardrail rather than a structural guarantee from having exactly one call site -- differs from A-E in that it doesn't unify the call sites at all, it polices them. I don't think this is as strong as A/B/C/D/E (it's a belt-and-suspenders addition, not a real fix for who gets the fitness dict), but it's worth naming so we don't converge on "the only way to avoid double-dispatch is a single call site" without considering the guardrail alternative. That's my full divergence set -- ready to move to evaluation.

## Decision Log
- [ACCEPT] B (split dispatch/score into two independently-callable pieces on BathosSplitComputeEvaluator; run_one_candidate_pass keeps its existing record_candidate_run dispatch unchanged, then calls the score-only piece with the output_paths it already has): Preserves AC-7's lineage/derived_from fail-loud wiring (unconfirmed whether the evaluator's own dispatch path threads parentage at all -- A/C risk silently dropping it). Structurally guarantees exactly one bathos dispatch call site per pass (satisfies #4137) without retiring already-tested code. Worst-case cost (BathosSplitComputeEvaluator turns out fused, not seamed) is a backward-compatible extract-method refactor, low blast radius on #4133's existing call site. OneCandidatePassResult gains a ratchet_decision field, resolving the accept/promote naming ambiguity in the bug report directly. Crash-atomicity and compile-time-clock attach post-decision inside this same function; compile-time-clock's in-process design vs out-of-process dispatch is flagged as an open sub-problem needing its own resolution (candidate self-reports both timings in its artifacts, or a separate in-process AOT probe), not a blocker to the winning architecture itself.
- [DEFER] E (relocate ratchet/scoring entirely to the future multi-iteration driver, leaving run_one_candidate_pass and OneCandidatePassResult unchanged): Runner-up. Steelman: main_loop.py's own docstring repeatedly and deliberately scopes campaign-lifecycle and error/retry concerns OUT of run_one_candidate_pass, pushed to LC-10 -- by the same logic, "current best"/ratcheting is inherently cross-iteration state a single pass has no standing to own, so E is more consistent with this module's documented scoping discipline than B, and carries zero regression risk to the already-shipped LC-09 contract. Counter, and why B still wins: GW-02's own cited bug is a property of OneCandidatePassResult.accepted itself ("a candidate strictly worse on every metric would still be marked accepted=True today") -- E doesn't touch that property, so a caller reading `accepted` in isolation is exactly as misled after E ships as before. E is deferred, not rejected: worth revisiting if/when LC-10's multi-iteration driver is actually designed, since it may turn out "current best" state naturally lives there anyway and B's ratchet_decision field could be layered on top of E's relocation rather than instead of it.
- [REJECT] A/C (replace or merge record_candidate_run's dispatch with BathosSplitComputeEvaluator's dispatch+score path outright): Unconfirmed whether BathosSplitComputeEvaluator's dispatch step forwards derived_from/parentage at all -- built for #4133's scoring concern, not AC-7's lineage concern. Replacing/retiring record_candidate_run risks silently dropping the fail-loud multi-parent-lineage protection AC-7 explicitly built. Larger blast radius than B for no clear architectural gain over B.
- [REJECT] D (protocol-level CandidateDispatcher/Evaluator abstraction over BathosSplitComputeEvaluator): Same end-state as A with extra indirection; over-engineering for a system whose lineage layer (AC-7) is explicitly documented as an interim awaiting a real mechanism, not a place to invest in abstraction now. No demonstrated second implementation ever needs to satisfy the protocol.
- [REJECT] F (dual-path dispatch-ledger guardrail instead of unifying call sites): Belt-and-suspenders, not a real fix -- doesn't solve who supplies the fitness dict, only polices against a second dispatch after the fact. Named during divergence for completeness, not a competitive architecture.

## Pre-mortem Record
**User:** Six months out, the shared scorer is being called from run_one_candidate_pass but nobody wrapped that call site in guarded_evaluate's track_reads()/verify_closure() audit context -- only BathosSplitComputeEvaluator.__call__'s own callers get that protection by convention, and the shared-scorer extraction made it trivially easy to call the scoring logic "bare" from a new site without carrying the audit wrapper along. This is exactly the failure mode PR #86's own follow-up (backlog #4136) already flagged for direct evaluator calls: bypassing guarded_evaluate silently drops closure_lock.py's path-leakage guard (UnlistedReadError) and the closure-hash-drift check (AC-7), so a candidate that reads outside its declared split_paths, or an evaluator whose closure has drifted since it was locked, would go undetected specifically on this new call path -- even though the exact same bug class is caught when scoring happens through the "proper" route. The mitigation: the shared-scorer function's contract must make the audit wrapper non-optional at the call site (e.g. the extraction takes the form of a guarded_evaluate-wrapping helper that run_one_candidate_pass calls, not a bare scoring function it could accidentally call unwrapped), and GW-02's own test suite must include a test that fails if a future edit calls the raw scorer without the wrapper -- not just a test that the ratchet math is correct.

  - [ ] `ratchet_crash_atomicity`'s exact protected failure mode: a process crash/kill between `create_pending_commit` (writes an unreachable, fsynced "tmp-commit" git object) and `advance_best_so_far` (the atomic `git update-ref` compare-and-swap that makes it the new best-so-far) never corrupts or loses the best-so-far ref -- `read_best_so_far` after restart returns either the pre-crash or the post-crash SHA, never a torn state, because each of the two steps is independently atomic at the git/OS level (fsync + `commit-tree`; CAS + `update-ref`). `run_one_candidate_pass` treats `CommitCreationError` and `RefUpdateConflictError` as fail-loud -- neither is caught and silently treated as "candidate not promoted"; a `RefUpdateConflictError` in particular means a concurrent writer moved the ref, which is a correctness bug (single-writer assumption violated), not routine candidate rejection.
  - [ ] `compile_time_clock` attaches AFTER the ratchet accept/reject decision, not before and not as an input to it: `measure_two_phase_timing`'s `TwoPhaseTiming.compile_time_seconds` (unit: **seconds**, per its own naming and `assert_no_compile_time_regression`'s `compile_time_seconds` parameter) is tracked as its own metric and checked via `assert_no_compile_time_regression` (default `k_threshold=3.0`, a dimensionless multiplier on that seconds value, against the caller-supplied rolling-median history), but `compile_time_seconds` is never merged into the fitness dict `multi_metric_ratchet.compute_ratchet_decision` compares -- only `runtime_seconds` (the cache-warm second call) is fitness-comparable. A `CompileTimeRegressionError` is raised loud (logged/escalated) independently of, and without blocking, the ratchet's own accept/reject outcome -- a compile-time blowup on an otherwise-improving candidate does not cause it to be rejected as a ratchet failure.
  - [ ] `OneCandidatePassResult` gains a `ratchet_decision` field populated only when scoring succeeded (guarded_evaluate returned a fitness dict without raising); `accepted` is redefined so a candidate that clears `stats_battery`/`seed_trial` but whose `ratchet_decision` is not an improvement is NOT `accepted=True` -- directly fixing the bug this item exists to fix (a candidate strictly worse on every metric currently reads `accepted=True`). The only current downstream consumer of `accepted`, `controller/multi_iteration_loop.py`'s `MultiIterationState` accepted-count property (`sum(1 for result in self.iterations if result.accepted)`, its docstring at L253-254) and the related comment at `main_loop.py:129`, must have its docstring updated to reflect the stricter (more correct) semantics -- no code change needed there since counting "was actually promotable" is what that property already intends.
