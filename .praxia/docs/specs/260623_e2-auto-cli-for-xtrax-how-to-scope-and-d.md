# Brainstorm: E2 auto-CLI for xtrax: how to scope and design a Tyro-delegated CLI (verbs plan/explain/sweep/run/resume/export) on top of E1's infer_bundle, given RunSpec is an eqx.Module with callable fields and run/sweep/resume/export are greenfield.

## Problem Frame
FIXED constraints: (1) Tyro owns arg PARSING — do not reinvent argparse (locked from E1). (2) The CLI must NOT change any existing runtime API signature (RunSpec, Engine, infer_bundle, the EDA layer stay as-is); the CLI is a NEW thin layer that consumes them. (3) Tyro/CLI deps go in a NEW `cli` optional-dependency extra — the core runtime stays slim; `pip install xtrax[cli]` is the affordance. (4) RunSpec's callable fields (carry_specs, boundaries) are NOT CLI-flag-expressible — this is a fact to design around (config-file or registration), not negotiable. (5) plan/explain must reuse E1's infer_bundle + the existing eda explain_plan/render — no reimplementation. (6) The CLI is also the machine interface an autoresearch orchestrator drives (so verbs should emit machine-readable output, e.g. --fmt json).

NEGOTIABLE (the forks): MVP verb scope (which of the 6 ship first); Tyro-delegated-thin-shell vs config-file-primary; how a fn/model is loaded (import-path my_pkg:sym vs config vs saved BundleSchema JSON artifact); sweep expression syntax; the resume run-manifest schema; whether `run` is even in the MVP given its greenfield wiring gaps; the package layout (xtrax.cli module, entrypoint name e.g. `xtrax`). Also negotiable and central: how AGGRESSIVE the MVP is — a tiny plan+explain showcase vs a fuller run-capable CLI. Frame confirmed on my end; please confirm and move to divergence.

## Idea Pool
- [ai] FACTION A — INSPECTOR MVP: ship ONLY the CLI scaffold + `plan` + `explain` verbs (plan = load fn -> infer_bundle -> BatchPlanner.plan -> show; explain = -> explain_plan -> --fmt {json default,text,html,png}). fn via import-path string (my_pkg:forward, resolved on sys.path); shapes as compact strings ('x=(4,3)f32'); ONE bespoke parser (_shapes.py). Tyro generates CLI from thin per-verb dataclasses. NO RunSpec config, NO model instantiation, NO manifests. Package xtrax/cli/, entrypoint `xtrax`, `cli` extra (tyro). json output = `PlanStatsDict` + _meta envelope (machine-readable for orchestrator: `xtrax explain --fmt json | jq`). run/sweep/resume/export ALL deferred E2.2+. STRENGTH: the wireable, zero-greenfield slice; it's the user-facing E1 smoke test E1 never shipped; decides import-path + --fmt conventions cleanly before RunSpec complexity. WEAKNESS: NOT run-capable — 'install xtrax, get a batch-plan viewer' reads as a toy to anyone expecting Hydra/MLflow; no answer to 'when can I run something?' except 'later'.
- [ai] FACTION B — FULL LIFECYCLE / CONFIG-PRIMARY: MVP covers plan/explain/run/resume/sweep (export deferred). A full experiment lives in a TOML config (RunSpec scalars + axes + [model] import-path + [optimizer] + [data] + [sweep] cartesian table); Tyro only routes the verb + accepts the config path/overrides (never parses TOML internals). BUILD the missing wiring as CLI-layer helpers (xtrax.cli._runtime, NOT public API): init_state(model,optimizer,seed)->ResumableState, run_from_config(config,engine) (loads model/opt via import-path, builds DataModule, writes RunManifest, drives Engine.fit_sync). RunManifest (.xtrax/runs/<run-id>/manifest.toml; run_id = first 8 hex of SHA256(canonical TOML); stores model import-path+kwargs so resume can rebuild the state_template then load_checkpoint). resume <run-id> = rebuild template -> load_checkpoint -> fit_sync remaining epochs. sweep = cartesian product over [sweep] scalars -> N run-dirs, sequential (--workers post-MVP). STRENGTH: a CLI that can't run an experiment is a README with a shebang; the missing wiring (init_state/run_from_config/manifest) is the correct abstraction xtrax needs anyway, and it eliminates every user writing their own harness. WEAKNESS (faction's own): LARGE greenfield with ~6 UNRESOLVED sub-forks — the DataModule factory interface is unspecified, the sweep executor (sequential-too-slow vs job-queue-scope-creep), config-hash determinism breaks on mid-run TOML edits, and string import pushes type errors to runtime. Any could block the sprint mid-flight.
- [ai] FACTION C — PROGRESSIVE SCAFFOLD / Tyro-delegated, staged verbs: ship a CLI that is ARCHITECTURALLY complete but functionally staged. E2-MVP = (a) the durable scaffold: `xtrax` entrypoint, `cli` extra, and a VERB-REGISTRATION pattern (xtrax/cli/registry.py: each verb is a self-contained module that calls register_verb(name, ArgsDataclass, run_fn, help); Tyro union-subcommand dispatch over the registry — adding a verb later = a ~20-line module + one import, NO router/entrypoint surgery); (b) the wireable verbs plan + explain (consume E1 infer_bundle + eda; --fmt json default); (c) ONE contained greenfield verb `export` (jax.export.export -> StableHLO artifact; small, self-contained, high-value for portability + autoresearch; doubles as a live integration test of the shared loader/emit infra). UNIFORM import-path loader (_load_fn: 'my_pkg:sym' via importlib) used by every verb — Tyro never sees callables, only strings, sidestepping the RunSpec-callable-field problem. SEAM (not build) run/sweep/resume: a --config TOML stub (scalar fields now, callable fields as import-path strings, validated) + a RunManifest dataclass stub, each with a DOCUMENTED gating question in verbs/_deferred.py. STRENGTH: the registration pattern + import-path loader are the real reusable assets — verbs become cheap ~20-line additions, extensible by construction, designed fresh before Engine-wiring pressure. WEAKNESS: stubs ROT if deferred verbs slip (architecture-astronaut risk); `export` adds genuine greenfield to the MVP (needs a jax.export-vs-infer_bundle smoke test before it's 'wired'). ## Decision Log
- [ACCEPT] E2-MVP locked scope (C-AMENDED, pre-mortem-trimmed): (1) scaffold = `tyro.extras.subcommand_cli_from_dict(REGISTRY)` over a module-level dict + `xtrax` entrypoint + new `cli` extra pinned to a tested tyro range; (2) verbs plan + explain ONLY (consume E1 infer_bundle + eda explain_plan; --fmt json default + text/html/png); (3) import-path loader that stores a STRING and resolves LAZILY at dispatch, wrapped in CLIImportError; (4) documented shapes-string grammar; (5) deferred verbs run/sweep/resume/export = ROADMAP NOTE ONLY, no stub code in the MVP.: Critic empirically verified the load-bearing pieces (tyro 1.0.15: subcommand_cli_from_dict gives clean verb names while a dynamic Union mangles them to `plan-args`; jax.export accepts ShapeDtypeStruct but .serialize() needs an undeclared flatbuffers dep + a format decision -> export is NOT thin, deferred). Net: A's tight zero-greenfield scope (plan+explain) + a cheap, non-rotting extensibility seam, with all over-engineering (custom register API, dynamic Union, export, speculative stubs) stripped out.
