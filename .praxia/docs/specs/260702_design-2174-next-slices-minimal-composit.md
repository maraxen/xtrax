## Pre-mortem Record
**User:** Six months out, the substrate shipped and #2181 was built on it, then it failed. The autopsy, most-likely first:

PM1 — ORDERED-SINK REORDERING (the runner-up's exact warning came true). The two-tier executor's ordered Tap/Sink inside scan/vmap looked correct in the AC4 counter-test on a toy scan, but under a real jit with XLA's latitude to reorder side-effect-free ops, the JEP-10657 token threading was subtly incomplete on one code path (vmap-of-scan). Records arrived out of order intermittently, non-deterministically, only at scale. Because D4 serialization and the D2 evaluator were already built on top, the fix touched the executor, the IR round-trip, and every recorded fitness run's provenance. This is the failure the steelman said Approach C would have caught in sprint 1. Mitigation that should have been in the spec: AC4 must test vmap-of-scan and scan-of-scan nesting, not a flat scan, and must run the counter-test under jit with donate/reorder stress, N times, asserting deterministic order every time — fast/loud on the FIRST out-of-order record.

PM2 — SEMANTIC-FAITHFULNESS BLINDSPOT SHIPPED ANYWAY. The benchmark AC (fork 12) was implemented, but under sprint pressure the "ground-truth-referenced faithfulness spot-check" got dropped and only the mode-vs-mode degradation delta shipped. It reported ~0% degradation, so constrained decoding was hardwired. Six months in, the #2181 loop is fed structurally-perfect graphs that compute the wrong thing; the fitness oracle (D2) is doing ALL the semantic work and is drowning in wrong candidates. The gate that was supposed to be cheap pre-filtering is filtering nothing semantic. Mitigation: the faithfulness spot-check must be a HARD sub-AC with its own success metric (e.g. ≥ N human-labeled tasks, report absolute faithfulness rate, FAIL the benchmark if only the delta is computed) — not a nice-to-have bullet.

PM3 — IR SCHEMA/E1 DRIFT SILENTLY BROKE OLD GRAPHS. schema_version was emitted but never CHECKED on load. E1 types churned (a new AxisOverride field), the emitter bumped to v0.2, but v0.1 graphs serialized months earlier still "loaded" — the loader tolerated the missing field with a default instead of failing. Old #2181 lineage graphs silently changed meaning. Mitigation: AC5 round-trip is insufficient; add a version-gate AC — loading a graph whose schema_version is unknown/older-than-min raises loudly, no silent default-fill of required fields.

PM4 — ADAPTER MASKED A REAL KEYING BUG. The fork-9 name-keying adapter silently deduplicated or dropped a boundary when two boundaries mapped to the same axis name (a real possibility with aminx positional construction). validate_plan_topology got a Mapping that was missing an entry it should have rejected, so an invalid plan passed. Mitigation: the adapter must raise on duplicate-axis-name collision, and there must be an AC proving list->Mapping adaptation is total and injective (no silent drop).

PM5 — io_callback SHIM ROTTED. The vendored shim pinned jax, but the pin was never enforced in CI; a transitive dep bumped jax, io_callback's signature moved, and the import-time assert was behind a code path that only fired at runtime, not import. Failures showed up as opaque tracebacks in the loop. Mitigation: the signature assert must fire at MODULE IMPORT (not first call), and a CI job must fail if the resolved jax version leaves the pinned range.

Top three by expected damage: PM1 (executor ordering — silent, at-scale, corrupts provenance), PM2 (faithfulness blindspot — poisons the whole #2181 value proposition), PM3 (schema drift — silently changes historical meaning). All three share a root cause: a gate that was specified as "checks X" but implemented as "tolerates not-X." Every AC in synthesis must state the fast/loud failure explicitly, and the three above need their success metric strengthened as noted.
