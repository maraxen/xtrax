## 0. The question this document answers

Marielle asked directly: **does praxia have a role in the controller?** She wants the design
pluggable to multiple dispatch systems in principle, with praxia as the concrete MVP backend. This
document answers that question with evidence, then proposes an architecture — it does not write
any code.

**Answer: yes.** The reasoning below traces to primary sources, not assumption.

## 1. The existing "zero praxia coupling" constraint is narrower than it first appears

xtrax's own `scripts/audit_dispatch_independence.py` (T2-21, AC-28, merged) is the actual
enforcement mechanism behind #2181's "zero praxia coupling" framing — reading it directly, not
just the DAG doc's prose summary, surfaces two things the summary doesn't carry:

- **Its scan target is `ROOT / "src" / "xtrax"` only.** The gate has nothing to say about code
  living anywhere else in the repo (or in a different repo entirely).
- **Its own docstring states the rationale as explicitly time-bound, not a permanent
  architectural rejection of praxia:**

  > "coupling to praxia today would make #2181 depend on two upstream praxia gaps: G1 (rig-run's
  > hardcoded 9-arm dispatch table), G2 (strict-mode tools are compiled Rust, so YAML flows can't
  > add new ones) — both tracked as praxia-repo T3 items, explicitly out of scope for this MVP."

  This was a sequencing decision — don't block #2181 on praxia's own then-unfinished
  infrastructure — not a stance that praxia is structurally wrong for this loop.

- **The same docstring says the runtime half of AC-28** ("success: loop runs end-to-end with
  praxia absent") **"is deferred until an actual #2181 loop controller lands."** The controller's
  own praxia-coupling status was always meant to be an open decision at build time, not a fact
  already settled by the gate. That build time is now.

## 2. G1 appears to have substantially evolved since the original 260702 decision

Checked the praxia repo directly (`/home/marielle/projects/praxia`) rather than trusting the
DAG's now-14-day-old framing:

- `mcp__praxia__rig_run`'s own tool description states it is now **"the sole microflow MCP entry
  (#3208)"** for recon/reviewer/summarize/research/impl and other flows — a unified,
  registry-style dispatch surface, not the fixed-arity table G1 described.
- `crates/praxia-rig-tools/src/rig_flow.rs` defines well over a dozen distinct named flow builders
  (`build_recon_tool_registry`, `build_impl_tool_registry`, `build_code_review_tool_registry`,
  `build_plan_audit_tool_registry`, etc.).
- The most recent commit in the praxia repo as of this writing (`4ac793740`, same day, 2026-07-16)
  is `feat(rig-tools): wire code_review_diff flow registry/dispatch/KNOWN_FLOWS` — active,
  ongoing expansion of the dispatch surface, not a static table.

This isn't independently verified to the same rigor as a merged AC — it's strong enough evidence
to design for praxia now, with the original G1 rationale explicitly flagged here as likely stale
rather than silently carried forward unexamined. If a future implementer finds G1 is still a real
constraint in some narrower sense, that's a correction to make at build time, not a reason to have
avoided this design pass.

## 3. Praxia's workflow schema is a natural mechanical fit for one loop iteration

Read xtrax's own already-merged workflow registration (T3-01): `.praxia/manifest.toml`'s
`[[plugin.workflows]]` entry pointing at `agent_assets/workflows/port_validation.yaml`. A praxia
workflow is a declarative DAG of `role_step` nodes, each carrying `role`, `agent_type`,
`role_capability`, a typed `gate: {kind: standard, verdict_enum: [...]}`, and a `prompt_hint`.

This maps directly onto #2181's own premise ("agentic algorithm evolution" — an LLM agent proposes
candidate mutations, deterministic gates keep it honest): one `role_step` dispatches an agent to
*propose* the next candidate mutation; the already-built walking-skeleton gates
(`assert_candidate_static`, `assert_schema_gate`, ..., `compute_ratchet_decision`) are exactly the
`gate: {kind: standard, verdict_enum: [advance, needs_work]}` checkpoints a workflow node already
expects. xtrax doesn't need to invent a new orchestration shape — it needs to reuse this one.

## 4. Proposed architecture

1. **A pluggable `DispatchBackend` interface** — an abstract "propose the next candidate mutation
   given context X, return a candidate" call. Praxia becomes a *concrete implementation* of this
   interface, not a structural dependency of the controller's own design. This leaves room for a
   future `ClaudeCodeBackend` or a raw-LLM backend without redesigning the controller around
   praxia specifically — directly satisfying "pluggable to multiple systems ideally."

2. **`PraxiaDispatchBackend`** (the MVP implementation) — calls `mcp__praxia__rig_run` (or
   whatever CLI/subprocess surface it wraps for a plain Python caller outside an MCP-connected
   session — an open question, see §5) to dispatch a mutation-proposal `role_step`, per the
   workflow-node shape in §3.

3. **The controller lives outside `src/xtrax/`.** This is the single most load-bearing placement
   decision: it means `test_dispatch_independence_gate.py` and `scripts/audit_dispatch_independence.py`
   keep passing **by construction** — nothing in `src/xtrax` ever imports praxia or calls
   `mcp__praxia__*` — rather than by exception, relaxation, or an allowlist entry. The controller
   instead *imports xtrax as a library* (already published on PyPI, `xtrax>=0.4.0a5`) to call the
   already-built gate functions in sequence, exactly the role every one of this epic's cross-repo
   modules (`xtrax.run.repro_floor`, `xtrax.loop.metrics_provenance`,
   `xtrax.loop.capability_probe_gate`, `xtrax.loop.stats_battery_gate`, and others) has explicitly
   deferred its own bathos-calling to all session: "the actual call happens one layer up, outside
   the module, by a future loop controller." This document's proposed controller *is* that future
   consumer. Dependency direction: controller → xtrax, never the reverse.

4. **Bathos calls happen at the same controller layer, same direction** — fulfilling that same
   "one layer up" deferral for every xtrax↔bathos crossing this epic already documented
   (`bth run`/campaign MCP tools, called by the controller, never by `src/xtrax` itself).

**Where exactly should the controller live?** Recommended default: a new top-level `controller/`
directory inside the xtrax repo — mirrors the existing precedent that `scripts/` already holds
non-packaged, non-`src/xtrax` code excluded from the wheel (`pyproject.toml`'s `packages =
["src/xtrax"]`), so this isn't a novel exception to the repo's own layout conventions. A genuinely
separate repo is the other real option (cleaner dependency-direction enforcement, but adds
cross-repo coordination overhead this epic doesn't yet need). **Left open for your decision, not
resolved here** — this document's job is to lay out the choice, not make it unilaterally.

## 5. Open questions (explicitly named, not silently assumed away)

- **Exact praxia CLI/MCP invocation mechanics from a plain Python process.** This session's
  `mcp__praxia__rig_run` calls happen from inside an MCP-connected Claude Code session. A
  standalone Python controller process (no MCP client) needs its own invocation path — likely a
  `praxia` CLI subprocess call, or a direct Rust-crate/FFI binding, or a lightweight MCP client
  library. Not resolved here; first thing a build-phase spike should nail down.
- **How a mutation-proposal `role_step`'s structured output maps onto the walking-skeleton's
  `candidate_path: Path, callable_name: str` contract.** An agent's proposal needs to land as a
  real file on disk with a resolvable callable before any gate can run against it — the exact
  hand-off mechanics (where the file gets written, naming, cleanup) aren't designed yet.
- **Bathos MCP call sequencing** — which specific calls (`campaign_create`, `run`,
  `campaign_conclude`, etc.) the controller makes at which points in the loop, and how their
  results thread into the caller-supplied dataclasses this epic's gates already expect
  (`CapabilityProbeResult`, `BathosStatsBatteryVerdict`, etc.).
- **Repo placement** (§4, above) — explicitly not resolved.

## 6. Phased build roadmap (sketch — not yet ACs, not yet a DAG)

A future planning pass should decompose this into real items once the architecture above is
validated, mirroring how #2181's own DAG only came after a research → brainstorm → adversarial-
review sequence (not skipped straight to implementation). Rough phase sketch, for that future
pass to refine rather than execute directly from here:

1. `DispatchBackend` Protocol + a trivial mock/deterministic backend (no praxia dependency yet) —
   proves the controller's own sequencing logic independent of any real dispatch system.
2. `PraxiaDispatchBackend` — resolves the invocation-mechanics open question from §5.
3. One real end-to-end iteration: mock or praxia-dispatched proposal → full walking-skeleton gate
   sequence (reusing the logic PR #61's smoke script already proved composes) → ratchet decision.
4. Bathos wiring — real campaign/run calls at the controller layer.
5. Multi-iteration loop — the actual "keep going" logic, budget/watchdog integration (T2-09
   already provides the primitive), diversity-quota Leap-Path triggering (T2-18 already provides
   the decision, not the mutation-generation response to it).
