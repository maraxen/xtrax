# Browser inference routes for aminx: jax-js, jax2onnx, and the int32/quantization question

## Why this exists

The question asked was whether all aminx models are available as xtrax-exported
fixtures and whether inference could be served from a GitHub Pages interface.
Both answers are no (§1). The follow-up — "what about jax.js, or other tools for
more direct conversion to WebGPU and wasm kernels?" — turns out to have a real
answer that is *better* than the IREE route we have been pursuing, and this
document records the measurement so the next reader does not re-derive it.

**The one-line finding:** `jax2onnx` converts Equinox models directly and covers
every `jax.lax` primitive aminx uses, so the browser is reachable today without
waiting on IREE. The catch is not op coverage — it is that ONNX *mandates* int64
indices on the exact operator aminx's k-NN and tiebreak paths lower to, and ONNX
Runtime Web's WebGPU backend does not support int64.

## 1. Starting state (measured 260914)

- **aminx exports nothing.** No `xtrax.export` import, no `export_pipeline`
  call, no tracked `.vmfb`/`.mlir`/`.wasm` anywhere in the repo. xtrax's own
  export fixtures compile a locally-defined `TinyMLP` and never reference aminx.
  The 0.4.0a10 repin installed the *capability* and its refusal gates; nothing
  calls them yet.
- **16 tracked checkpoints, 110 MB total** under `src/aminx/model_params/`:
  ~5.9 MB each for `proteinmpnn`/`solublempnn` `v_48_*`, 9.3–13 MB for
  `ligandmpnn` `v_32_*`, 6.5 MB for the membrane variants.
- **IREE still has no WebGPU backend.** Re-measured today against the pinned
  `iree-base-compiler 3.11.0`:
  `cuda  llvm-cpu  metal-spirv  rocm  vmvx  vmvx-inline  vulkan-spirv`.
  No `webgpu`, no `webgpu-spirv`. Blocked upstream on
  [iree#24650](https://github.com/iree-org/iree/issues/24650), open since
  2026-06-29.

## 2. jax-js is a reimplementation, not a converter

[ekzhang/jax-js](https://github.com/ekzhang/jax-js) is a from-scratch
implementation of the JAX/NumPy API in JavaScript that JIT-compiles to WebGPU
and wasm kernels. Performance is real: >7000 GFLOP/s matmul on an M4 Max under
WebGPU, and the fastest multithreaded in-browser wasm matmul (~2× XNNPACK).

**It does not ingest Python JAX models.** No StableHLO, no `jax.export`, no
serialized-program path. There are exactly two ways in:

1. rewrite the model in JavaScript against its API, or
2. load an ONNX file through its `@jax-js/onnx` package.

So for our purposes jax-js is **not an export target** — it is one of several
*runtimes* that can consume an ONNX file. That reframes it entirely: the
interesting work is upstream of it. Maturity is early (~927 stars at time of
writing, no production-readiness claim); `@jax-js/loaders` reads safetensors and
caches large weight downloads in OPFS.

## 3. jax2onnx is the actual bridge — and it speaks Equinox

[enpasos/jax2onnx](https://github.com/enpasos/jax2onnx) converts JAX, Flax NNX,
Flax Linen, and **Equinox** callables to ONNX. aminx models are Equinox, so
there is no reimplementation step. It also ships an explicit `export_mode="web"`
and a browser/WASM validation workflow.

Primitive coverage, read off the autogenerated table
(`docs/user_guide/jax_lax_coverage.md`) rather than the README:

| Primitive | Status | Relevance to aminx |
|---|---|---|
| `cond` | direct plugin | `utils/coordinates.py:51` backbone-noise branch |
| `scan` | direct plugin | autoregressive decode |
| `sort` | direct plugin | the `num_keys=2` tiebreak from aminx PR #156 |
| `top_k` | direct plugin | k-NN selection |
| `gather`, `scatter`(+`_add/_max/_min/_mul/_sub`) | direct plugin | feature assembly |
| `while_loop` | covered indirectly (via `while`) | |
| `rng_bit_generator`, `rng_uniform` | direct plugin | |

**The table contains zero `not_covered` rows.** Unsupported primitives fail
loudly with an explicit error rather than silently miscompiling, and the plugin
system is the documented extension path.

Note what this does to our live IREE blocker: `lax.cond` traces both branches,
which is why RNG is in the graph even at `backbone_noise=0` and why the IREE
path is stuck. `cond` converts cleanly here, so that specific blocker is not
inherently a blocker on this route.

## 4. The int32 question — aminx is already 32-bit; ONNX is not

This was the sharpest part of the question, and the answer has two halves that
point in opposite directions.

**Half one — aminx's own graph is already int32.** `jax_enable_x64` is never
enabled in `src/`; the only uses are a `tests/ebm/conftest.py` fixture that sets
and restores it. JAX therefore operates in 32-bit by default, so every traced
array is `int32`/`float32`. The `int64`/`float64` occurrences in the tree
(`host/_sampling_grid_lineage.py`, `parity/evidence.py`,
`ebm/ddg_stability.py`) are host-side NumPy that is never traced into an export.
So *we* are not the source of any int64.

**Half two — ONNX mandates int64 anyway, and that is the collision.** The ONNX
spec constrains `TopK`'s index output to `tensor(int64)` — it is not a choice
the exporter makes. And jax2onnx's `lax.sort` plugin
(`jax2onnx/plugins/jax/lax/sort.py`) lowers sort to **`TopK` + `GatherElements`**
and explicitly stamps the indices `INT64` at lines 190-191.

Meanwhile ONNX Runtime Web's **WebGPU execution provider does not support
int64**; the wasm EP supports all operators. So the int64 index tensors land
precisely on the WebGPU backend's known dtype gap — and they land on the index
path, which is the exact path that has already produced two silent bugs in this
model (tie order, random permutation).

**Consequence:** int32 is not something we need to *adopt* — we are already
there — it is something an ONNX toolchain would need to *narrow back down to*,
offline, after export. That is a standard transform, but on this model it is a
correctness-relevant one rather than a perf tweak, and it must be verified by
comparing emitted indices, not logits.

Practical ordering that falls out of this: **wasm EP first, WebGPU second.**
wasm supports every operator and every dtype; WebGPU is the optimization, and
it is the one that can silently change integer results.

## 5. HYPOTHESIS (unverified): multi-key sort re-introduces a stability dependency

aminx PR #156 replaced inherited sort stability with an explicit index tiebreak
— `jax.lax.sort((-x, index), num_keys=2, is_stable=False)` — specifically so
that no backend's tie handling could permute the result. That was the right fix
and it remains correct in JAX.

But jax2onnx's sort plugin implements multi-key sort as a **radix pass over keys
in reverse order** (`for key_idx in reversed(range(num_keys))`, sort.py:115),
emitting one `TopK` per key. An LSD radix sort is only correct if **each pass is
stable**: the index pass runs first, then the value pass must preserve that
ordering for equal values.

If ONNX `TopK` does not guarantee stable tie order — and ONNX Runtime's WebGPU
and wasm EPs need not agree with each other about it — then the tiebreak aminx
added is re-exposed to exactly the failure class it was written to eliminate,
one layer down in the ONNX graph.

**This is a hypothesis, not a finding.** It has not been tested. It is written
down because it is cheap to test, it is invisible to float parity, and it is the
single most likely way this route produces a green check over wrong output. See
[[reference_iree-breaks-jax-stable-sort]] for the identical failure on the IREE
route.

## 6. Quantization — the acceptance metric has to change

Weight size is **not** the constraint here. A single `proteinmpnn` checkpoint is
~5.9 MB compressed (~6.8 MB raw fp32) — trivially downloadable. fp16 halves it,
int8 quarters it. The 110 MB figure only matters if you intend to ship all 16
checkpoints to the browser, and GitHub Pages' limits (100 MB/file, ~1 GB repo)
would accommodate even that. **Quantize for latency and memory if profiling says
to, not for download size.**

The real issue is what quantization does to *this* model's output. aminx emits a
**discrete sequence**, selected by argmax/top-k over logits. Every export defect
found so far has been an integer divergence with bit-identical floats. Coarsening
the logits:

- makes exact ties **more** frequent, not less, which increases dependence on the
  tie-order behaviour §5 flags as unverified;
- can flip an argmax between two near-equal amino acids while leaving logit MSE
  and `allclose` looking excellent.

So the acceptance criterion for any quantized aminx artifact must be
**sequence identity / recovery rate against the JAX oracle**, not logit MSE, not
`allclose`, and not float `max_abs_diff`. jax2onnx's own docs recommend
`allclose` for parity — that is necessary and **not sufficient** for this model.
Suggested ladder, cheapest-first: fp32 → fp16 → int8 weight-only/dynamic on
linear ops, stopping at the first tier where sequence recovery degrades.

## 7. What this route would change architecturally

Under IREE, weights **bake into the module as constants**, so the artifact
matrix is `checkpoints × buckets` — which is what forced the
`(64,128,256,512,1024,1536,2048)` ladder and its ~28 MB bundled tier.

Under ONNX, weights are **initializers in a single file** and jax2onnx supports
symbolic dimensions. If sequence length can be made a symbolic dim, the bucket
ladder may collapse to **one artifact per checkpoint**. That would be a large
simplification.

Flagged as a hypothesis, with a specific reason for doubt: jax2onnx's own
limitations page says not every JAX shape-polymorphic expression is
representable in ONNX, and aminx's `k = min(k_neighbors, L)` clamp
(`model/features.py:183`) is exactly the kind of shape-dependent expression that
tends not to survive. The padding-invariance result (score-preserving iff
`L ≥ k_neighbors`) means bucketing remains a correct fallback if dynamic `L`
does not convert.

## 8. Route comparison

| Route | Browser today? | Blocker |
|---|---|---|
| IREE `wasm32` | no | CODEGEN_ONLY; needs an emsdk-built IREE runtime, no published package |
| IREE `webgpu` | no | backend absent from every published wheel; iree#24650 |
| IREE `native-portable` | no | x86-64-v2 ELF, needs local IREE runtime |
| **jax2onnx → ORT Web (wasm)** | **yes** | int64 fine here; slowest tier |
| **jax2onnx → ORT Web (WebGPU)** | **yes, with caveats** | int64 unsupported → offline narrowing; op subset |
| jax2onnx → @jax-js/onnx | plausible | jax-js maturity unproven for this model |
| jax2onnx → wonnx | plausible | Rust/WebGPU, less exercised |
| rewrite in jax-js | yes | full model reimplementation, ongoing divergence risk |

## 9. Recommended next step

A bounded spike, roughly a day:

1. `jax2onnx` one checkpoint (`v_48_020`) at a fixed bucket length ≥ 48.
2. Run under ORT Web **wasm** EP, then **WebGPU** EP.
3. Diff against the JAX oracle on **both** logits *and* emitted indices/sequence
   — the index diff is the whole point; a float-only check passes vacuously here.
4. Record whether ONNX `TopK` preserved the §5 two-key tiebreak, and whether the
   wasm and WebGPU EPs agree with each other on ties.
5. Only then try dynamic `L` (§7) and the quantization ladder (§6).

This reuses the parity discipline already built for the IREE path and answers the
viability question without committing to the route.

## 10. What is NOT claimed here

- jax2onnx has **not** been run against an aminx model. Coverage-table support is
  not the same as "it converts."
- §5 (sort stability) and §7 (dynamic `L`) are hypotheses with stated reasons,
  not measurements.
- No statement is made about Firefox or Safari WebGPU status.
- This does not supersede
  `.praxia/docs/specs/260910_webgpu-export-route.md`; that spec governs the IREE
  route's verification levels and its constraint — *no artifact may imply browser
  compatibility without browser-execution evidence* — applies verbatim to
  everything above.
